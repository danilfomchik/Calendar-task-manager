# Open-Meteo and browser geolocation for Day Conditions

The Day context's Conditions block (weather, sunrise, sunset, moon phase for the Viewed day) gets its data from Open-Meteo, called straight from the browser through an RTK Query API (`src/redux/conditions/conditionsApi.ts`). We picked it because the app has no backend and Open-Meteo needs no API key and allows CORS, so no secret ships in the bundle (unlike the Groq key behind AI insights). It also covers past days as well as forecasts. Two hosts are used. `api.open-meteo.com/v1/forecast` serves 92 days back to 15 days ahead. `archive-api.open-meteo.com/v1/archive` (ERA5 reanalysis, from 1940) serves older days. The card is hidden outside that range. Open-Meteo does return a `moon_phase` daily value, but it is not defined in the API docs. Because of that, the moon phase is computed locally from the date (`moonPhase.ts`), the same way for both hosts.

The location comes from the browser's Geolocation API, and the app asks for it **once**. The position is rounded to two decimals (about 1 km) and stored in `localStorage` (`conditionsLocation`) with the user's answer (`granted`/`denied`). After that, every Viewed day reuses it, and a denial is never re-prompted. The trade-off is that the rounded coordinates, along with the date and the user's IP address, go to a third party (Open-Meteo, Germany) every time an uncached day is looked up. We accept this because the precision is coarse, there is no account or identifier attached, and asking is opt-in. When no location is known (permission denied, or no position available), the card shows a "Set location" prompt instead of disappearing. The prompt opens a city search on Open-Meteo's geocoding API (`geocoding-api.open-meteo.com/v1/search`, the `searchPlaces` endpoint in the same RTK Query API). The search runs only when the user submits it, never on each keystroke, so only the text they submit leaves the browser, and never a position. The picked city is rounded the same way and stored in the same `conditionsLocation` entry (`source: 'city'`, plus a display name such as "Lisbon, Lisbon District, Portugal"). The stored `denied` answer is kept as it was. A "Change" control on the card opens the same search at any time, so a device position that has gone stale after a move can be replaced without being asked for location on every visit. Switching back to the device position is offered from the same search ("Use my location"), which asks the browser again and reports why it failed; the stored answer is updated by the new result.

Until a location is saved, Conditions uses an **approximate location**: the city nearest the browser's time zone, from a small table bundled with the app, so nothing is sent anywhere to choose it. It is never stored, is labelled as approximate, and is replaced by the device position if that arrives. The "Set location" prompt remains only for a time zone the table does not cover.

## Considered options

- **OpenWeatherMap / WeatherAPI and similar**: these need an API key, which would be public in a client-only app. Free tiers have no long history.
- **IP-based location**: no prompt, but it still sends the user's IP to a third party, it is often wrong by a whole city, and it is less transparent than an explicit permission prompt. The bundled time-zone table gives a coarser default with no extra request.
- **Asking for geolocation on every visit**: fresher position, but it repeats a permission prompt (or a silent lookup) the user has already answered.
